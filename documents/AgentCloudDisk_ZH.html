摘要

用户越来越愿意把文件存到云端，但主流网盘除了存字节几乎不做别的，数据也基本只有在用户主动分享时才会流通。于是大量有价值的资源沉淀在各类主体的个人与企业网盘中，包括业务台账、实验记录、行业报表、归档文档与结构化数据表；这些文件具备潜在价值，却长期处于沉睡状态——现有工具既无法识别它们装了什么，也无法把它们归集成一件完整的东西，更无法把它们供给给愿意为之付费的人。本文演示 AgentCloudDisk，一个把大模型 Agent 与网盘耦合起来的可运行系统，使持有者能把原始数据产出为数据产品，并把该产品当作一项供给。给定一句话描述，Agent 选择聚合模板，只解析持有者勾选的文件夹，在网盘所在主机内把内容归约为 k-匿名聚合，附上可复现的构建凭证，并上架到数据市场，由买方发布需求、接收匹配到的货源。协同机制把同一套耦合扩展到多个持有者：一段短协同号即可加入，多方各自贡献统计而非文件，联合产品随成员加入而增大。整个过程默认没有任何文件内容离开其持有者。观众可以在一次浏览器会话内把一个文件夹变成已上架产品，并用一段协同号加入联合产品。

1 引言

云存储已成为个人与组织文件的默认去处。用户越来越愿意把文档放进云端，其中的材料体量也在持续增长。然而主流网盘的设计本质上仍是存储服务：它接收上传、按文件名取回文件，并把"分享"当作让数据抵达他人的唯一途径。于是数据只有在用户刻意分享时才流通，而现实中这往往意味着它根本不流通。

其后果是沉睡价值的大规模沉积。有价值的资源散落在各类主体的网盘中：业务台账、实验记录、行业报表、归档文档与结构化数据表，躺在为某个团队、某个目的建立的文件夹里。这些文件具备潜在价值，持有它们的各方往往也愿意供给，但材料之所以继续沉睡，是因为从"一个文件夹"到"一件可上架的产品"之间横着三道障碍。第一道是识别：没有任何网盘知道某个表格文件夹记的是通勤时间而不是库存数量。第二道是归集：一堆原始数据行不是任何人能够检验、定价或接受的产品。第三道是保护：持有者有理由拒绝公开可能包含客户姓名、证件号或商业敏感记录的文件。

大语言模型（LLM）恰好适合攻克第一道障碍，因为它们能理解用户意图并阅读异构内容；近期研究也表明，基于 LLM 的 Agent 能够规划、调用工具并代表用户行动 [10]。然而现有系统对后两道障碍基本没有作答。文件助手继承网盘自身的权限模型，而那套模型是为"分享给人"设计的，不是为"委托给一个会调用第三方模型的进程"设计的。数据市场系统假设已经存在整理好的数仓，从而绕开了"数仓如何形成"这一问题。联邦学习回应了保护问题 [13]，但它产出的是模型，而非可核查的产品。真正缺位的是一种系统：它接受网盘本来的样子——内容异构、且部分敏感——并把其中选定的部分变成供给。

为补上这一缺口，我们提出 AgentCloudDisk，一个把 Agent 与网盘耦合、并将网盘原始数据产出为数据产品的系统。这一耦合围绕三个面组织。权责面把 Agent 限制在持有者勾选过的文件夹内、并限制为该持有者的身份，使访问是受限的而非弥漫的。暴露面把解析、去标识与聚合留在网盘所在主机内，使模型只收到有界摘录、买方只收到聚合结果。溯源面为每个产品附上构建凭证，把它绑定到读过的源文件哈希与被它拒绝的文件，使上架内容无需访问网盘即可核对。同一套耦合还能跨持有者组合：一段短协同号引入协作者，各自运行自己的受限绑定，贡献分组统计而非文件。

我们以可运行的演示系统实现该设计，并用六套脚本化测试在 REST 接口上断言用户可见行为。本文贡献可概括如下：

• 我们把网盘数据的沉睡问题界定为一个供给问题而非存储问题，并识别出造成"文件夹无法成为产品"的三道障碍：识别、归集与保护。

• 我们实现了一种 Agent 与网盘的耦合，在网盘所在主机内化解这三道障碍，使模型默认不接收任何文件字节，且每个产品都带有买方可以核验的凭证。

• 我们证明该耦合可以跨持有者组合，使多个网盘共同供给同一个联合产品，而没有任何文件离开其持有者的机器。

后文依次介绍系统的设计与实现（第 2 节）、演示流程（第 3 节）、实现要点与伦理考量（第 4 节）、验证（第 5 节）、局限（第 6 节）与结论（第 7 节）。

2 系统设计与实现

2.1 从沉睡的文件夹到已上架产品

图 1 展示了我们实现的耦合。网盘是底座，Agent 站在其上，三个面把两者连接起来，各自回应上文识别出的一道障碍。权责面是持有者看到的那一层：一句描述目标产品的话（Agent 把它转成模板选择），以及一棵可勾选的文件夹树。Agent 得到的不是路径前缀，而是一份按持有者持久化的范围记录，每次打开文件都要与该记录核对。暴露面由网盘自身承担：解析、敏感信息扫描与聚合都在网盘主机内执行，于是模型收到的是有界摘录，买方收到的是聚合结果。溯源面是凭证，它随 Agent 的工作逐步写入，并与产品一同发布。

图 1. 一个 Agent 与一个网盘之间的耦合有三个面，其中只有暴露面与溯源面会在网盘之外产生可观察物。

2.2 Agent 究竟需要网盘的什么

值得精确说明哪些网盘原语与 Agent 相关，因为这解释了耦合为何不能简单复用分享链接。如图 2 所示，文件树对应受限读取，内容字节对应流式读取，持有者身份对应归属，分享链接对应受众控制。

图 2. 网盘原语投影到 Agent 需求上：文件树变成受限读取，内容字节变成流式读取，持有者身份变成归属，分享链接变成受众控制。

文件树对应受限读取，因为 Agent 必须只枚举被授予的子树，并且要能确信枚举行为不会把该子树撑大。内容字节对应流式读取，因为 Agent 必须处理超过内存的文件，以及模型无法直接吞下的格式。持有者身份对应归属，因为每个产品都要能追溯到一个可问责的主体，这正是联合产品的发布权必须留给发起方的原因。分享链接对应受众控制：链接给人的是某个文件的宽泛访问，而 Agent 需要的是对某个计算结果的窄访问。因此本系统不向 Agent 暴露分享链接，也不暴露路径前缀，只给它一份范围记录、一个流式读取器和一支写凭证的笔。

2.3 访问生命周期

图 3 追踪一次请求在五条泳道上的流转。Agent 先绑定到一个范围，向模型询问模板，然后严格在范围内读取。每一块数据都要先过主机侧扫描器才可使用，命中扫描器的文件被排除，原因写入凭证。存活的行被聚合，只有聚合结果离开网盘。随后 Agent 解绑，范围被释放，凭证关闭。

图 3. 一次请求在五条泳道上的访问生命周期。网盘只在绑定范围内打开字节，模型从不接收字节，凭证写在网盘一侧。

这个生命周期有两点对演示很重要。第一，模型不在数据通路上：它为模板选择提供建议、协助描述结果，但默认没有任何文件内容经过它。第二，凭证写在数据所在之处，因此不会被被审计方改写。

2.4 守住边界

只有当检查是显式的而非涌现的，耦合才可信，因此我们把它实现为一条守卫链，如图 4 所示。打开文件的请求在以下情形被拒绝：落在勾选范围之外、调用者不是记录上的持有者、或主机侧扫描发现标识信息。通过扫描但超出单次模型预算的文件会被裁剪而不是丢弃，裁剪同样被记录。每个分支都写下结果，使被拒绝的读取与成功的读取一样可见。

图 4. 每次打开文件前都要经过的守卫链。拒绝与排除都会被记录，而非静默发生。

2.5 暴露边界

图 5 以显式清单的形式陈述这条边界。左列永远不离开网盘，包括原始文件、图片与压缩包、完整文档、明文密钥、个体的每一行，以及任何本身已带标识信息的文件。右列是可以越界的部分，即持有者的那句话、按字数限定的摘录、持有者显式要求的图片、分组聚合以及凭证。

图 5. 什么留在网盘内、什么可以离开。这条分界线源于设计，而非源于配置。

有界摘录值得单独说明，因为它是唯一可能把源自文件的文本送到模型处的通道。该通道上限为每文件 1200 字符、每次调用 6 个文件；正文已含身份证号、手机号、银行卡或搬运特征的文件会在任何调用发出之前被过滤，因此该上限作用于已经干净的文本。

2.6 跨网盘供给联合产品

单个持有者的网盘常常不足以支撑一个值得上架的产品，因此同一套耦合可以横向组合，如图 6 所示。多个持有者各自保留自己的范围、各自执行主机侧归约，只交换分组统计。发起方得到一个 8 位协同号与 6 位协同密码，其字母表刻意去掉了 0、O、1、I，以便口述；兑换两者的协作者在提交任何数据之前会先看到邀请预览。合并是在分组键上取并集，每个分组都附带一个记录支撑网盘数量的字段，这正是联合产品能随成员加入而变大的原因。

图 6. 协同就是把同一套耦合按持有者各做一遍。每个网盘在本地归约，中心只观察到分组统计。

发布权仍归发起方，因为即使数据来自多方，归属也必须落在一个可问责的主体上。因此市场把联合产品与单方产品同等对待，仅以溯源标记与凭证中的贡献者列表区分。

3 演示

演示沿着一个文件从沉睡文件夹走到已上架产品的路径展开，观众无需离开浏览器即可走完全程。

3.1 描述产品

观众从权责面开始，输入诸如「把我记录的通勤时间整理成按线路的平均耗时」这样一句话。Agent 回以模板、置信度、一句话理由，以及它打算产出的字段。模板选择分两遍进行：规则匹配器按关键词重合度为每个内置模板打分，并总能给出答案；当配置了模型时，再由大模型对候选重新排序。系统内置四个模板，分别是通勤时效统计、家常菜谱库、宠物喂养记录与读书笔记主题。固定模板集是刻意的，因为产品之间必须保持可比。

3.2 受限读取

观众随后勾选一个或多个文件夹并开始构建，此时暴露面变得可观察。弹窗逐文件流式显示事件，例如读取、解析、跳过、带原因排除，最后给出产品卡，报告分组数、参与文件数与质量分，并附四行聚合预览。正文带标识信息的文件在任何模型调用之前即被排除，卡片上用平实语言陈述这条隐私规则。若描述与勾选的文件夹不一致，卡片会报告这一不一致，而不是给出一个空白产品。

3.3 协同

为演示跨持有者的耦合，讲者创建一个联合产品，并把 8 位协同号连同密码递给一位观众。在提交任何数据之前，该观众会看到邀请预览，列出标题、发起方、当前成员以及产品将包含的字段。勾选文件夹并加入后，分组数立即上升且双方都能看到，而只有发起方的界面带有发布控件。

3.4 供给与核验

买方用自然语言发布需求，市场返回带可读理由的排序推送。随后观众可以打开一个货源，核对其中没有源文件名、没有个体行，并且其凭证记录的哈希与卖方贡献的文件一致。最后以三状态握手收尾：买方申请交付、卖方受理、卖方标记为已交付，全程不传数据体。

4 实现与伦理

该耦合实现在单个 Spring Boot 与 Kotlin 进程内，上述各个面对应的是模块而非部署单元。

有三处实现选择塑造了这一设计。范围以记录而非路径前缀的形式保存：授权范围按持有者、按协同成员持久化，并在协同页回显，这多花一张表，却让撤销与审计变得简单，并允许从成员自己的范围重算其贡献。流式读取是主机侧归约可行的前提：表格逐行读、Word 通过流式 XML 拉解析器读、PDF 通过手写字面量解析器读、图片通过本机光学字符识别读、压缩包受控解包。敏感扫描器在块边界之间保留 32 字符尾部窗口，因此被切在两次读取之间的证件号依然会被检出，而这个细节之所以重要，正是因为读取是流式的。最后，凭证充当产品的契约：它记录源文件哈希、聚合参数、若咨询过模型则记录模型版本，以及每条带原因的排除，使买方可以在不访问网盘的前提下用证据核对一个上架内容。

全部演示数据为合成数据；系统设计为只打开勾选的子树，授权范围被持久化并回显给持有者。聚合满足 k-匿名，默认 k 为 3。正文已带个人标识的文件在任何模型调用之前于主机侧被过滤；模型返回的证据必须在解析正文中逐字出现，否则替换为本地片段。平台密钥以 AES-256-GCM 加密，主密钥置于数据库之外；协同密码以哈希保存、只显示一次，且任何接口都不会返回。

6 局限

有三点局限值得直接说明。模板集是封闭的，落在四个内置模式之外的请求只会以较低置信度落到最接近的模板，而不会生成新的抽取规则，这意味着系统出售的是聚合表格，而非任意数据产品。并集合并是务实做法而非形式化隐私保证：它阻止了记录交换并丢弃稀疏分组，但若有对手用重叠范围反复加入，理论上仍可能通过差分把分组收窄，这正是我们计划改用差分隐私估计量的动因。最后，耦合是按请求而非持续的：Agent 在一次构建期间持有范围，随后释放，因此既没有常设授权，也没有「长期观察某个文件夹」的 Agent 概念。

7 结论与未来工作

本文论证了网盘数据的沉睡问题是一个供给问题，而非存储问题。我们展示了与网盘耦合的 Agent 只需从网盘借到三样东西，即受限的权责、主机侧归约边界与凭证，就足以让持有者把一个沉睡的文件夹变成已上架产品、跨网盘协同，而任何文件都不离开其机器。未来工作方面，我们计划开放模板层使持有者可以定义自己的聚合模式，把并集合并替换为差分隐私估计量，并研究「持续耦合」，即 Agent 在常设授权下长期观察某个文件夹。
